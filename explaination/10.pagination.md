pagination is achived by frontend and backend

# What is a URL query string (the `?page=2&limit=6` part)
The stuff after `?` in a URL is how the frontend tells the backend what it wants.
```
http://localhost/api/events/list.php?page=2&limit=6
                                     └─────┬─────┘
                                       query string
```
- `?` means "parameters start here"
- `page=2` -> one parameter named `page` with value `2`
- `&` splits parameters
- `limit=6` -> another parameter named `limit` with value `6`

So the browser is saying: "give me page 2, and 6 items per page".
The backend reads these with `filter_input(INPUT_GET, 'page', ...)`.

# The 2 formulas that make pagination work
Say we have 20 events, and show 6 per page.
```
skip (how many rows to jump over) = (page - 1) * limit
total_pages                       = ceil(total / limit)   ->  ceil(20 / 6) = 4
```
| page | skip | shows rows |
|------|------|------------|
| 1    | 0    | 1-6        |
| 2    | 6    | 7-12       |
| 3    | 12   | 13-18      |
| 4    | 18   | 19-20      |
The database is told: "skip `skip` rows, then take `limit` rows" -> we get exactly one page.

# backend (pagination.php) for function definition
There are 3 helper functions. In one line each:
- `readPaginationParams` -> read `page`/`limit` from the URL, clean them, and calculate `skip`.
- `clampPagination` -> after we know the real total, if the page number is too big, pull it back to the last page.
- `paginationMeta` -> pack the info (which page, how many pages, has previous/next) to send back to the frontend.

## Function 1: readPaginationParams -> "which page does the user want?"
`filter_input(...FILTER_VALIDATE_INT)` reads the value and checks it is an integer.
If the user sends junk like `page=abc`, it returns false, so we fall back to a default.
`min($limit, $maxLimit)` stops someone from asking `limit=999999` and killing the server.
```php
function readPaginationParams(int $defaultLimit = 6, int $maxLimit = 50): array
{
    $page = filter_input(INPUT_GET, 'page', FILTER_VALIDATE_INT);
    $limit = filter_input(INPUT_GET, 'limit', FILTER_VALIDATE_INT);

    $page = $page !== false && $page !== null && $page > 0 ? $page : 1;
    $limit = $limit !== false && $limit !== null && $limit > 0 ? $limit : $defaultLimit;
    $limit = min($limit, $maxLimit);

    return [
        'page' => $page,
        'limit' => $limit,
        'skip' => ($page - 1) * $limit,
    ];
}

// Build the pagination metadata object returned by list endpoints.
function paginationMeta(int $page, int $limit, int $total): array
{
    $totalPages = max(1, (int) ceil($total / $limit));
    $currentPage = min($page, $totalPages);

    return [
        'page' => $currentPage,
        'limit' => $limit,
        'total' => $total,
        'total_pages' => $totalPages,
        'has_previous' => $currentPage > 1,
        'has_next' => $currentPage < $totalPages,
    ];
}

// Clamp a requested page to the actual available page range before querying data.
function clampPagination(array $pagination, int $total): array
{
    $totalPages = max(1, (int) ceil($total / $pagination['limit']));
    $page = min($pagination['page'], $totalPages);

    return [
        ...$pagination,
        'page' => $page,
        'skip' => ($page - 1) * $pagination['limit'],
    ];
}
```

## Function 2: clampPagination -> "pull a too-big page back"
Example: the user edits the URL to `page=100` but there are only 4 pages.
Without this, the DB skips too many rows and returns a blank page.
`min($page, $totalPages)` -> `min(100, 4) = 4`, so it jumps back to the last page.
It needs `$total`, so we must call `countDocuments()` BEFORE calling it.

## Function 3: paginationMeta -> "the info sheet for the frontend"
When we send the data back, we also attach this small "info sheet" so the
frontend knows the current page, total pages, and whether the prev/next
buttons should be enabled.
- `ceil()` = round up (20/6 = 3.33 -> 4 pages)
- `has_previous` / `has_next` are true/false, used to grey out the buttons.

# Read the pagination to know how many pages that the user want, get the total posts, and then check the clampPagination, if the pages is over, then take it back
```php
$pagination = readPaginationParams();

// Only active posts are visible in public feeds.
$query = [
    'status' => 'active',
];
$total = $posts->countDocuments($query);
$pagination = clampPagination($pagination, $total);
```

# use the cursor to record the current statement of the pages
```php
$cursor = $posts->find(
    $query,
    [
        'sort' => [
            'created_at' => -1,
        ],
        'skip' => $pagination['skip'],
        'limit' => $pagination['limit'],
    ]
);
```

# respond the current pagination status by using pagination meta including the current status like which page, what is the previous and last page.
```php
respond(200, [
    'success' => true,
    'posts' => $postList,
    'pagination' => paginationMeta($pagination['page'], $pagination['limit'], $total),
]);
```

# frontend (app.js)
The whole site loads ONE app.js, so every list (events, my registrations,
community posts...) shares the same code. It uses a `state.pagination` object
to remember which page each list is on. Each list has a name called `key`
(the events list key is `'events'`).
```js
state.pagination = {
    events:        { page: 1, limit: 6 },  // events list is on page 1
    registrations: { page: 1, limit: 6 },
    communityPosts:{ page: 1, limit: 6 },
}
```
The frontend only does 2 jobs: (1) tell the backend which page to load,
(2) draw the "1 2 3 ..." buttons.

## Step 1: build the query string -> paginationParams(key)
Turns the saved state into `page=2&limit=6` and sticks it on the request URL.
This is where the frontend and backend connect.
```js
function paginationParams(key) {
    const current = state.pagination[key];          // {page:2, limit:6}
    return `page=${current.page}&limit=${current.limit}`;
}
```

## Step 2: save the backend info sheet -> setPagination(key, pagination)
Stores the returned meta (page, total_pages, has_next...) into
state.pagination[key], so we can draw the buttons later.

## Step 3: draw the buttons -> pageNumbers + renderPagination
`pageNumbers` decides WHICH numbers to show. With 100 pages we can't draw 100
buttons, so it only shows: first page, last page, current page and its
neighbors, with `...` in the middle. On page 50 you see:
```
1 ... 49 50 51 ... 100
```
`renderPagination` turns them into HTML buttons. Each button carries 2 small
`data-` tags: which list, and which page to go to.
```html
<button data-pagination-key="events" data-pagination-page="3">3</button>
        └── which list ──┘         └── go to page ──┘
```

## Step 4: handle the click -> handlePaginationClick(event)
When the user clicks "page 3":
```js
const key  = "events";   // read from the button's data- tag
const page = 3;

setPagination(key, { page });   // set events current page to 3
await renderEvents();           // re-request page 3, only refresh that panel
```
Note: only that one panel reloads, NOT the whole website. That's why it feels smooth.

# The full loop
```
you click "page 3"
  -> handlePaginationClick sets state events.page = 3
  -> renderEvents builds ?page=3&limit=6 and calls the backend
  -> backend: readPaginationParams reads page=3 -> skip=12 -> take rows 13-18 -> return data + info sheet
  -> setPagination saves the sheet -> renderPagination redraws the buttons, page 3 highlighted
  -> you see page 3
```
